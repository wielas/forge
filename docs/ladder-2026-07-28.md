## Rung 1 — a real repo, no agents

New variable: none. Stamp the template, install the hooks, and attack the local
gates by hand.

### R1-F1 — the pre-push branch guard fails open, and checks the wrong remote

**Severity: high** (for an advisory guard). Confirmed 3×.

`lefthook.yml`'s `no-main-push` decides whether a push to `main` is a legitimate
bootstrap by asking whether `main` already exists on the remote. Two defects:

1. **It asks the wrong remote.** It resolves `branch.<b>.remote`, falling back
   to `origin` — that is the remote the branch *tracks*, not the one git is
   pushing to. The two differ whenever a second remote exists.
2. **It reads any error as permission.** `git ls-remote --exit-code --heads`
   exits non-zero for "this remote has no main" *and* for "no such remote",
   "network down", "auth failed", "GitHub is having a day". The guard treats all
   of them as "must be a bootstrap, allow it".

Reproduction — a direct push to a `main` that demonstrably already existed on
the push target, allowed because an unrelated `origin` was unreachable:

```console
$ git remote add origin git@github.com:wielas/does-not-exist-xyz.git
$ git ls-remote --heads probe main | wc -l
1                                     # probe DOES have main
$ git push probe main
┃  no-main-push ❯
bootstrap: origin has no main yet — allowing the push that creates it
   92d6fa8..8084069  main -> main     # ← the push the guard exists to block
```

The fix is available and was not known to be: **lefthook substitutes git's hook
argv into the `run` template**, so `{1}` is the remote actually being pushed to.
Measured on 2.1.10 — the exact belief that this was impossible is R1-F2.

```console
$ git push probe HEAD:refs/heads/probe-args-test
TPL1: probe TPL2: /private/tmp/.../ladder-remote.git   # {1}, {2}
ARGS: [] [] []                                          # $1, $2 — empty
--- stdin follows ---
--- stdin end ---                                       # stdin NOT forwarded
```

So: the remote name **is** reachable (`{1}`), the destination refs are **not**
(stdin). When the hook is invoked by hand with no args, `{1}` is left as the
literal four characters `{1}` — not empty — so a fix must detect that.

### R1-F2 — the "KNOWN HOLE" comment is false for `pre-push`

**Severity: medium** (it is wrong, and it argues future maintainers out of a
fix). Confirmed 3×.

Both `templates/.../lefthook.yml` and `scripts/verify.sh` carry an emphatic,
"measured", explicitly-do-not-revisit comment claiming that when a push carries
no changed files, lefthook skips **every** pre-push command, so an empty commit
bypasses both the branch guard and `make check`.

On lefthook 2.1.10 this does not reproduce. Pushing a pure empty commit onto an
already-pushed branch runs both commands:

```console
$ git commit --allow-empty -m "probe: P5 truly empty delta"
$ git push probe feat/probe3
│  lint (skip) no files for inspection     ← pre-COMMIT, expected
│  fmt  (skip) no files for inspection     ← pre-COMMIT, expected
┃  full-check ❯   FORGE CHECK: GREEN       ← pre-push RAN
┃  no-main-push ❯                          ← pre-push RAN
   fe19b58..fc77bb8  feat/probe3 -> feat/probe3
```

What was originally observed was almost certainly the pre-**commit** skip above
— `fmt`/`lint` do carry `{staged_files}` and correctly skip when nothing is
staged. Commands with no file template run regardless.

### R1-F3 — `python_version` is a floor, not a pin; the venv is not the documented version

**Severity: medium.** `copier.yml` asks for `python_version` (default `3.12`)
and spends it on two things: `requires-python = ">={{ python_version }}"` and a
line of AGENTS.md prose. Neither pins anything, and no `.python-version` is
stamped, so uv picks the newest interpreter it can find:

```console
$ .venv/bin/python -V
Python 3.14.6
$ grep Python AGENTS.md
- Python 3.12, uv-managed. src layout: `src/ladder_forge/`.
```

The project's own SSOT states a version the project does not use. More
importantly CI resolves its interpreter independently, so ADR-0003's claim that
`make check` in CI is *identical* to local holds for the command but not for the
runtime under it. Severity is capped at medium pending the CI-side measurement
(rung 1 remainder — needs the GitHub repo).

### R1-F4 — `make new` tells the operator to run `git init`, not `git init -b main`

**Severity: low, latent.** Everything downstream hardcodes `main`: the branch
guard, `ci.yml`'s `push: branches: [main]`, and `make protect`'s
`branches/main/protection`. `make new` prints:

```
→ cd ../ladder-forge && git init && make setup && claude (/scope)
```

On a host where `init.defaultBranch` is not `main` that produces a `master`
repo in which every gate is silently inert — no error, just nothing enforced.
It passed here only because this host sets `init.defaultBranch=main` globally.
`README.md`'s quickstart already says `git init -b main .`; the Makefile hint
disagrees with it.

### R1-F3, quantified against real CI

With no pin, the two sides of ADR-0003 resolved **two minor versions apart**:

```console
$ .venv/bin/python -V                      # local
Python 3.14.6
$ gh run view 30359752903 --log | grep CPython
Using CPython 3.12.3 interpreter at: /usr/bin/python3.12   # CI
```

After stamping `.python-version`, local is 3.12.13 and CI is 3.12.3 — same
minor series, still different patch. `.python-version: 3.12` pins the series,
not the patch; the AGENTS.md line says exactly that rather than claiming more.

### The merge gate, attacked rather than read

Four probes against `wielas/ladder-forge` with `make protect` active. The local
hook is advisory and two of these walk straight past it; the wall is off-host.

| # | Attack | Local hook | GitHub |
|---|---|---|---|
| G1 | `git push origin main` | **BLOCKED** (correctly resolved the real origin via `{1}`) | — |
| G2 | `git push --no-verify origin main` | bypassed | **rejected** — "Changes must be made through a pull request" |
| G3 | `git push origin HEAD:main` from a feature branch | bypassed (blind to refs, as documented) | **rejected** |
| G4 | merge a PR whose CI is red | — | **refused**, `mergeStateStatus=BLOCKED` |
| G4b | same merge with `--admin` | — | **refused** — `Required status check "check" is failing` |

G4b is the one worth keeping: `enforce_admins: true` means the gate holds
against the operator's own account, which is what makes it a gate and not a
convention. Both G4 attempts were made after CI had actually gone red, not
against a pending check.

rejected the first attempt for formatting, which is the gate doing its job.

`make verify` after the fixes: **40 passed, 0 failed, 1 skipped** (was 38/0/1;

### Not a finding — confirmed still true

- `git push <remote> HEAD:main` from a feature branch bypasses the guard
  (`8084069..8090b33 HEAD -> main`). Genuinely uncatchable: the destination refs
  arrive only on stdin, which lefthook does not forward (measured above). The
  existing comment is right, and branch protection is the answer.
- `--no-verify` and `LEFTHOOK=0` bypass the hook entirely. Inherent to hooks.

### R2-F1 — `make check` returned a green that CI rejected

**Severity: high.** This is the one that matters: it defeats §5, which is the
lane's *only* defence against a fabricated green.

`make check` was green in the worktree — twice for Codex, once for me running it
plain as §5 demands. CI then failed the PR on `I001`, un-sorted imports.

Same commit, same locked ruff 0.16.0, same command, three ways:

```console
# in the lane worktree, as the lane runs it
$ uv run ruff check .
All checks passed!

# same directory, same bytes, cache removed
$ rm -rf .ruff_cache && uv run ruff check .
Found 1 error.

# cold clone of the same commit
$ git clone --branch chunk/c2-truncate … && uv run ruff check .
Found 1 error.
```

Resolved settings are identical between the two (`--show-settings` diff is only
the path prefix), so it is the cache, not the config. **The precise
invalidation bug inside ruff is not pinned** — replaying it synthetically by
restoring violating bytes at the original size and mtime did *not* fool ruff, so
something subtler is going on. The effect is reproducible and that is what
counts here.

Why it is severe rather than annoying: §5 exists so that CI never has to catch
a chunk. Here the order reversed. A cached verdict is not a verdict, and a lane
that trusts one is back to trusting Codex's self-report.

**Fix:** the template's `lint` target now runs `ruff format --check --no-cache`
and `ruff check --no-cache`. CI is always cold, so this makes local and CI the
same command in fact and not merely in spelling. `fmt` keeps its cache — it
mutates, it does not judge. `forge-lane` §5 gained the escape hatch for
projects stamped before the fix (`rm -rf .ruff_cache`).

New verify case `template/check-reads-no-cache` asserts the flags. It is a
config assertion on purpose: with the staleness not synthetically reproducible
there is no honest behavioural test to write, and the flag going missing is
exactly how the false green returns.

### R2-F2 — `--add-dir` hands Codex the entire shared `.git`

**Severity: medium, accepted-and-bounded rather than closed.**

The flag `forge-lane` §4 requires for committing inside a worktree grants far
more than committing. The sandbox banner states the scope plainly:

```
sandbox: workspace-write [workdir, /tmp, $TMPDIR, /Users/goonlab/dev/ladder-forge/.git]
$ ls /Users/goonlab/dev/ladder-forge/.git
hooks info logs objects refs worktrees COMMIT_EDITMSG config description …
```

So a run can write `hooks/` — the whole L2 local tier — `refs/heads/main`,
`config` (remotes), and every other worktree's admin dir. Codex did none of
this, and the lane had no way to notice if it had.

Not closed by narrowing: git needs objects, refs and the worktree admin dir
together, and a wrong guess breaks committing inside a worktree, which cost a
whole rung to get working. Closed by *detection* instead — §5 now records
`git rev-parse main` and the hooks dir's status before §4 and compares after,
and treats a difference as a block rather than a retry. The wall (branch
protection) is off-host and unaffected by any of this.

### R2-F3 — `make setup` in a worktree rewrites the *main* repo's hooks

**Severity: low. Validated, and deliberately not fixed.**

`git rev-parse --git-path hooks/pre-push` resolves to the common dir, so §3's
`make setup` writes the shared hook — and lefthook bakes the *installing*
checkout's venv path into it:

```console
$ grep .venv /Users/goonlab/dev/ladder-forge/.git/hooks/pre-push
  elif /Users/goonlab/dev/ladder-forge/.worktrees/rung2/.venv/…/lefthook -h …
```

The main checkout's gate now points inside a worktree, and concurrent lanes
race on one file. Tested the consequence directly — removed the worktree, then
pushed to main from the main checkout:

```console
$ git worktree remove --force .worktrees/rung2
$ git push origin main
FORGE CHECK: GREEN
BLOCKED: direct push to main. Chunks land via PR.
```

The guard still fires: lefthook's generated script has a fallback chain and
lands on `uv run lefthook`. So the finding is real but currently harmless, and
the honest call is to record it rather than spend a fix on it. Worth knowing
that the chain's last resort prints "Can't find lefthook in PATH" and exits
**0** — a silent pass — but reaching it requires a checkout with no venv, which
also has no hooks installed.

### R3-F1 — the tier-2 human card was dispatched to a lane; tier 2 collapsed into tier 1

**Severity: high.** This is the finding of the run.

`forge-prejudge.SOUL.md` is explicit — `initial_status="blocked"`, and the
comment beside it reads *"no assignee: a human owns this, not a lane"*. What
was actually created:

```console
$ hermes kanban show t_745725d6 --json | jq '{assignee,status,created_by}'
{ "assignee": "forge-prejudge", "status": "running", "created_by": "forge-prejudge" }
```

The dispatcher claimed the human's review card and handed it back to the same
profile — and the same cheap model — that had just approved the work. ADR-0007's
two-tier design was defeated in the only direction that matters: tier 2 became a
second tier 1.

What stopped a self-approval was not a gate. That run read its own card, noticed
it should not be there, and blocked itself:

> Tier-2 judge card dispatched to wrong profile (forge-prejudge instead of
> human). Needs human to run /judge on PR #4.

Good judgement, and exactly the wrong thing to depend on.

**The parameters are not at fault** — measured on the same board minutes later:

```console
$ hermes kanban --board forge-ladder create "probe" --initial-status blocked --json
{"id":"t_515d05c3","assignee":null,"status":"blocked"}
```

Unassigned + blocked works exactly as the SOUL describes. The model simply did
not pass what it was told to pass. More prose will not fix a prose failure, so
the approve path now has to **prove** the card landed right: read it back,
assert `assignee` is empty and `status == "blocked"`, repair with
`kanban_update` and re-read if not.

Note what `make verify` did here: `lane/prejudge-approve-routes-to-tier2`
**passed** through all of this, because it checks that the SOUL *says*
`kanban_create`. The text was right and the behaviour was wrong — L1 persuading
where L2 should enforce, in the one place the repo cannot put a real gate. New
case `lane/prejudge-tier2-card-is-read-back` at least requires the proof step
to exist.

### R3-F2 — `--json` shapes differ per subcommand, and jq answers a wrong path with silence

**Severity: medium, operational.** `hermes kanban create --json` returns a flat
object with `.id`; `boards list --json` returns a bare array; `show --json`
nests everything under `.task`, with run metadata under `.runs[]`. Nothing in
the repo records this.

It cost real time twice in one run. `.status` on `show --json` returned `null`
for four minutes while the card was in fact `running`, and `.metadata` returned
`null` while complete `forge.chunk.v1` metadata sat under `.runs[]`. Neither was
an error — jq returns `null` for a wrong path, so a monitoring loop reports
"nothing happening" just as confidently as if nothing were happening.

`board-bootstrap.sh` depends on two of these three shapes, so a Hermes change
here would break dispatch silently rather than loudly. New case
`substrate/kanban-json-shapes` pins all three — this is exactly the "behaviour
we depend on and do not control" the substrate group exists for.
