## Facts that constrain the design `[V]`

**Kanban worker model.** Workers are dispatcher-spawned *Hermes profiles* driving
the board through `kanban_*` tools. An unknown assignee does **not** fail loudly:
the dispatcher drops the card, it sits in `ready` forever with a
`skipped_nonspawnable` event, and it only surfaces in `hermes kanban diagnostics`
as `stranded_in_ready` after `kanban.stranded_threshold_seconds` (30 min).
Every assignee must exist before a card names it. *(Corrected 2026-07-27 from the
bundled `KANBAN_GUIDANCE` + `kanban-worker-lanes.md`; the earlier "auto-blocks
after two spawn failures" was wrong.)*

**Toolsets are a live trap.** `custom_toolsets:` is documented
(`website/docs/reference/toolsets-reference.md`) but **no code in 0.19.0 reads
it**. A profile whose `toolsets:` names a custom bundle resolves to zero tools —
verified with `toolsets.resolve_toolset('forge') -> []`. `toolsets:` must list
real toolset names, one per line (`toolsets.get_toolset_names()`). `messaging` is
not one of them.

**Workspaces.** `scratch` is **deleted on completion**; chunk cards must use
`worktree`. A `worktree` workspace is created **worker-side** — the worker runs
`git worktree add` itself from the main repo, using `$HERMES_KANBAN_BRANCH` when
set, and the result is preserved on completion. Board resolution falls back to
the persisted current board, so every forge `kanban create` must pass `--board`
explicitly or cards land on `digest`.

**Worker protocol.** Exiting 0 while the task is still `running` is a
`protocol_violation` → auto-block, run wasted. Always end with `kanban_complete`
or `kanban_block`. Heartbeat at least hourly on long work. With
`terminal.timeout=1800`, a **synchronous** delegation under ~30 min is safe (stale
reclaim is 4h) — cap chunk size instead of building background/poll machinery.

**Bounce dynamics are board-native.** The respawn guard already refuses re-spawn on
`blocker_auth` (quota/auth), `recent_success`, and `active_pr`. Add `--max-retries`
per card; don't invent a bounce loop.

**`approvals.mode` cuts both ways.** `manual` (current) makes an unattended worker
wait for an approval nobody can give; `off` checks nothing on a `local` backend
with a reachable bot. **`smart` is the only mode that is both safe and viable.**

**`claude -p` works from the gateway** — proven by having Hermes itself run it
(`is_error:false`). But: it defaulted to **Opus**, and consumed ~20k tokens of
auto-discovered context (hooks, skills, plugins, MCP, CLAUDE.md) to answer "OK".
So **pin `--model`** in the lane and **keep the mini's `~/.claude` lean** — every
MCP server installed there is paid for on every invocation. `--bare` would skip
that context but **cannot read `CLAUDE_CODE_OAUTH_TOKEN`**, and the only
alternative credential is a metered API key, so the lane runs non-bare and states
its mode explicitly (`--bare` is slated to become the `-p` default).
`total_cost_usd` is computed locally at list rates and is **not a bill** on a
subscription — keep it as a relative signal, never as spend.

**Auth.** Credentials live in the macOS Keychain, which a non-GUI session may not
unlock. `claude setup-token` mints a **one-year** subscription token; it belongs in
`~/.hermes/.env` so the gateway injects it into children. No auto-refresh —
**silent expiry would kill every lane, so cron the renewal date.**
`ANTHROPIC_API_KEY` outranks it in the precedence order, which is why the money
invariant is a gate rather than a note.

**Both `claude -p` and `codex exec` read stdin.** Always redirect `< /dev/null`, or
they consume whatever the parent had queued. `codex exec` also refuses to run
outside a git repo — fine inside a worktree — and takes `--output-schema` for
structured verdicts (`claude -p` uses `--json-schema`). Together these replace the
`FORGE_METADATA_BEGIN/END` stdout-scraping hack.

**codex-cli 0.145.0 has no `--full-auto`.** The sandbox flag is
`-s {read-only|workspace-write|danger-full-access}`. Inside a worktree the real
`.git` lives in the main repo, so committing also needs
`--add-dir "$(git rev-parse --git-common-dir)"`. Both the old `codex-worker.sh`
and Hermes's own bundled `kanban-codex-lane` skill still say `--full-auto` — they
are stale, ours is verified against `codex exec --help`.

**Profiles** are separate `HERMES_HOME` directories created with `hermes profile
create <name> --description "<role>"`; the description feeds orchestrator routing.
There is no `profiles:` block in `config.yaml`.

**Unresolved `[A]`:** Hermes runs a **curator** that reviews, archives and rewrites
agent-managed skills. `install.sh` symlinks git-tracked forge skills into that
directory. If the curator can edit through the symlink, methodology drifts outside
version control silently. Settle before running `install.sh` — currently latent
(0 symlinks present).

## Decisions `[D]`

**D1 — lanes are Hermes profiles, not an external puller.** A profile reads the
card, drives `codex exec` in the worktree, verifies, opens the PR, completes with
metadata. Hermes owns claim, reclaim, retries, circuit breaking, logs, dashboard.

**D2 — Codex implements, Claude judges, in two tiers.** Tier 1 `forge-prejudge`
bounces the obvious (ci-red, scenario theater, scope creep) unattended. Tier 2 is
the operator tapping `/judge` in Claude Code — subscription-covered, zero marginal
cost, and a better fit for "judge report + spot-checks" than fighting it.
Auto-merge only when judge-approved **and** tagged low-risk at roadmap time.

**D3 — the money invariant is a gate.** No metered tokens for implementation or
deep review; bounded OpenRouter aux calls are the only sanctioned metered surface.
Enforced as a lane precondition (`preflight.sh` §2).
